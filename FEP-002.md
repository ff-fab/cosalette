# FEP-002: Deferred `enabled=` for Telemetry and Device Decorators

**Status:** Proposed **Date:** 2026-04-20 **Author:** cosalette-apps maintainer
**Target:** cosalette >= 0.4.x

## Problem

The `@app.telemetry()` decorator's `enabled=` parameter only accepts a literal `bool`.
When the enabled/disabled decision depends on runtime settings, adopters cannot use the
decorator form and must fall back to imperative `add_telemetry()` inside
`@app.on_configure`.

This breaks the "declarative `main.py`" goal: if even one device has a
settings-dependent `enabled=`, _all_ devices must move to `on_configure` for consistency
— otherwise the module mixes decorator registrations at module level with imperative
registrations inside the configure hook.

### Concrete example (gas2mqtt)

```python
# Desired — fully declarative, all devices visible at module level:
@app.telemetry("magnetometer", interval=lambda s: s.poll_interval,
               enabled=lambda s: s.enable_debug_device)  # ← NOT SUPPORTED
async def magnetometer(mag: MagnetometerPort) -> dict[str, object]:
    reading = mag.read()
    return {"bx": reading.bx, "by": reading.by, "bz": reading.bz}
```

```python
# Actual — forced into on_configure because of enabled=:
@app.on_configure
def setup(settings: Gas2MqttSettings) -> None:
    app.add_telemetry("gas_counter", gas_counter, ...)
    app.add_telemetry("temperature", temperature, ...)
    app.add_telemetry("magnetometer", magnetometer,
                      interval=settings.poll_interval,
                      enabled=settings.enable_debug_device)  # only reason we're here
```

### Precedent

`interval=` already supports `Callable[[Settings], float]` for deferred resolution via
`resolve_intervals()` in `_wiring.py`. The `enabled=` parameter has no equivalent — it's
consumed at decoration/registration time and not stored in `_TelemetryRegistration`.

## Proposed solution

### Accept `Callable[[Settings], bool]` for `enabled=`

Extend `enabled=` to accept either a `bool` or a `Callable[[Settings], bool]`. When a
callable is provided, the decision is deferred to the bootstrap phase — after settings
resolution, alongside `resolve_intervals()`.

**Decorator usage:**

```python
@app.telemetry("magnetometer",
               interval=lambda s: s.poll_interval,
               enabled=lambda s: s.enable_debug_device)
async def magnetometer(mag: MagnetometerPort) -> dict[str, object]:
    reading = mag.read()
    return {"bx": reading.bx, "by": reading.by, "bz": reading.bz}
```

**Implementation sketch:**

```python
# 1. New type alias (alongside existing IntervalSpec)
type EnabledSpec = bool | Callable[[Settings], bool]

# 2. Add enabled field to _TelemetryRegistration
@dataclass(frozen=True, slots=True)
class _TelemetryRegistration:
    ...
    enabled: EnabledSpec = True  # NEW — stored instead of consumed at decoration time

# 3. In decorator: always register, store the enabled spec
def decorator(func):
    # Don't skip registration when enabled is callable — defer the decision
    if not callable(enabled) and not enabled:
        return func  # literal False: skip as before
    ...  # register with enabled=enabled stored in the registration

# 4. New resolution function in _wiring.py (parallel to resolve_intervals)
def resolve_enabled(
    telemetry_list: list[_TelemetryRegistration],
    settings: Settings,
) -> None:
    """Resolve callable enabled specs and remove disabled registrations."""
    to_remove = []
    for i, reg in enumerate(telemetry_list):
        if callable(reg.enabled):
            if not reg.enabled(settings):
                to_remove.append(i)
            else:
                telemetry_list[i] = dataclasses.replace(reg, enabled=True)
    for i in reversed(to_remove):
        telemetry_list.pop(i)

# 5. Call resolve_enabled() right after resolve_intervals() in _run_async
```

### Validation timing

When `enabled=` is callable, eagerly-validated constraints (`persist=` requires
`store=`, `triggerable` + `group` exclusion, etc.) must be deferred. Two options:

**A. Defer all validation when enabled is callable (recommended):** Skip persist/store
and other checks at decoration time when `enabled` is callable — the device might end up
disabled anyway. Run validation only after `resolve_enabled()` confirms the device is
active. This is the simpler path and matches how `interval=` callable already defers its
validation.

**B. Always validate eagerly:** Validate constraints even when `enabled` is callable.
Cleaner error messages but raises errors for devices that will never run.

### Scope

Apply to all three registration decorators:

| Decorator          | `enabled=` today | Proposed                             |
| ------------------ | ---------------- | ------------------------------------ |
| `@app.telemetry()` | `bool`           | `bool \| Callable[[Settings], bool]` |
| `@app.device()`    | `bool`           | `bool \| Callable[[Settings], bool]` |
| `@app.command()`   | `bool`           | `bool \| Callable[[Settings], bool]` |

The imperative `add_telemetry()`, `add_device()`, `add_command()` functions continue to
accept only `bool` — they already run inside `on_configure` where settings are
available.

## Advantages

- **Fully declarative `main.py`** — every device visible at module level with all
  metadata (interval, publish, persist, enabled) in one place
- **No `on_configure` needed** for apps whose only settings dependency is interval and
  enabled
- **Follows established precedent** — exact same pattern as `interval=` callable
- **Backward compatible** — literal `bool` still works identically
- **Small implementation surface** — one new resolution function, one new field

## Disadvantages

- Slightly more complex decorator validation flow (deferred when callable)
- `_TelemetryRegistration` gains a new field
- Registrations exist briefly before being pruned — minor memory overhead

## Impact

- **gas2mqtt**: Can move from `on_configure` to fully decorator-based module level
- **Any app with optional/debug devices**: Same benefit
- No breaking changes
